# dsh 0.1.5 兼容性复盘

> 背景：dsh 0.1.5 对 web 端做了多处破坏性变更，`dsh-enhance`（主题层）与 `dsh-desktop`（桌面壳）都在受影响范围内。
> 本文记录「官方改了什么 → 我们怎么适配 → 怎么验证 → 下次升级怎么自查」，供下一次官方动刀时照着查。

## 一、官方 0.1.5 的破坏性变更

### 1. 浏览器入口需要认证

- `dsh web` 启动时打印的入口带一次性 token：`dsh web: http://127.0.0.1:3080/?token=xxxx`
- 该 URL 请求后 `303 → /`，并 `Set-Cookie: dsh-auth-…`；cookie 值形如 `v1.<base64url(payload)>.<base64url(HMAC-SHA256)>`
- cookie **与 authority 绑定**（name 与载荷都含 `new URL('http://' + Host).host`），默认有效期 30 天
- 无有效 cookie 的**导航请求**得到 401（非导航请求是 404，容易误判）；响应体是一行纯文本，白底无样式
- 签名密钥持久化在 `$DSH_HOME/.credentials.yaml` 的 `client-connection/browser-session` 记录中：

  ```yaml
  client-connection/browser-session:
    kind: grant
    payload:
      version: 1
      secret: <32 字节 base64url>
  ```

**受影响的既有实现**

- 启动脚本用 `curl -sf` 探测「后端在不在」会拿到 401 → 被判为失败 → 误判成「没启动」→ 重复拉起一个抢不到端口的后端，白等 150 秒
- 桌面壳直接 `loadURL(TARGET)` 会撞 401，窗口里只有一行纯文本

### 2. `dsh web` 默认打开系统浏览器

0.1.5 起 `dsh web` 默认把 Web UI 塞给系统默认浏览器；桌面壳自己就是那个浏览器，必须显式 `--no-open`，否则每次启动多弹一个窗口。

### 3. 亮色主题 token 拍平为冷白

官方 light 把 `bg-base` / `bg-layer-1..3` 全部取值为 `#fff`，并新增/改写了一组「凸起面」与代码面 token
（`bg-module-platform`、`bg-multi-select`、`markdown-code-segment-selected`、`markdown-placeholder`、
`markdown-tag`、`button-ghost-active-hover`，以及静态色 `--dsw-static-neutral-50/100`）。
暖色主题若不覆盖，会在奶油底上露出白框（主题选中框、语言/权限/字号选择器、卡片激活态等约 18 处）。

### 4. `theme` 服务延迟就绪

`@deepseek-ai/dsh-client-ui-theme` 的 fiber 注入是 `["slots", "locale", "remote", "settingsScope"]`，
要等宿主连接（remote）与设置作用域就绪后才 `provide("theme")`。插件若不声明 inject，
`apply` 阶段一次性 `ctx.get("theme")` 会拿到 `undefined`，覆盖层被静默跳过 ——
表现为「浅色底色回落到官方纯白」，且没有任何报错。

### 5. 其余实测确认无碍的变更

- **dockkit 标签页 / 分栏系统**：隐藏 panel 停在视口外（x 恒等于视口宽 + 1，与窗口宽度无关），
  `分栏 / 全屏 / 收起右侧边栏` 等按钮因此不在视口内 —— 这是官方布局，浏览器里同样如此，不是壳造成的
- **全局 `corner-shape: superellipse(1.5)`**：壳注入的悬浮按钮圆角会跟着变成超椭圆，属预期观感

## 二、适配方案

### 认证：双通道

| 场景 | 通道 | 实现 |
|------|------|------|
| 壳自己拉起后端（冷启动） | 官方 token 入口 | 启动脚本从后端日志抓 `?token=` URL，经 `DSH_AUTH_URL` 传给壳，壳直接 `loadURL` |
| 复用你自己开的后端 | 凭证自签 cookie | 壳读 `.credentials.yaml` 的签名密钥，按官方 v1 载荷 + HMAC-SHA256 自签一枚等价 cookie 写入 Electron session |

自签 cookie 的逐字段约束（对齐官方 `dsh-client-connection` 的 `BrowserAuth`）：

- cookie 名：`dsh-auth-` + `base64url(sha256(authority))`
- authority：`new URL(TARGET).host`（与请求 Host 头一致；`URL` 规范化会去掉默认端口、小写化主机名）
- 载荷字段：`{ version: 1, authority, issuedAt, expiresAt }`，且 `expiresAt - issuedAt` 不得超过官方
  `cookieMaxAgeDays`（默认 30 天），否则验签后仍被时间窗拒绝
- cookie 值：`v1.` + `base64url(JSON.stringify(payload))` + `.` + `base64url(HMAC-SHA256(secret, body))`
- 必须 `httpOnly + sameSite=strict`，与官方 `sessionCookie()` 的写入属性一致

失败兜底：两条通道都拿不到 cookie 时，壳显示可操作的中文提示页（解释原因 + 给出两条恢复动作），
而不是把官方的一行 401 纯文本留在窗口里。

### 主题：Solarized 作为可选叠加层（不注册进官方主题表）

改造前插件用 `!important` 无条件接管官方浅色。现在改成「设置 → 通用 → dsh-ux 配色」里的
一个开关，但**没有**走官方主题注册表 —— 实测发现官方对第三方主题的支持不完整：

- `theme.register({ id, colorScheme, tokens })` 确实接受第三方主题（注释写明
  "third-party themes register alias-layer overrides"），`setTheme(id)` 也能切换并广播 `theme/change`
- **但** `ThemeRuntime.setTheme` 只在 `isThemePreference(id)` 时写 settings，而 `ui-theme` 段的 schema 是
  `z.union(["light", "dark", "system"])` —— 第三方 id **存不进去**
- 更麻烦的是 `adopt()`：settings 就绪或变化时会把内存偏好**覆盖回** settings 里的内置值。
  刚 `setTheme('dsh-ux')` 成功的偏好，会在下一个 tick 被打回 `light`（tab 一刷新就丢）
- 连带坑：用「先写迁移标记、再 setTheme」的写法，一旦 setTheme 抛错（主题尚未注册），
  这次失败会被当成"已迁移"，之后永不重试

所以改用**独立开关通道**：

| 机制 | 实现 |
|------|------|
| 色值 | 顶部单一 CSS 闸门块：`html:not([data-dsh-ux-theme="off"]) body:not([data-ds-dark-theme]) { … }`（68 个 token = 原 21 个 alias + 47 个 specific/静态） |
| 状态存储 | 一枚 cookie：`dsh-enhance-theme=on\|off`（不碰官方 settings） |
| 首帧 | host 侧 `webserver/index-inject` 注入内联脚本读 cookie，在任何渲染前写 `data-dsh-ux-theme` |
| 开关 UI | 自建设置行，注册进 `settings.general.item`（order 20，排在官方外观行之后） |

这个形状换来几个性质：与官方主题偏好**零冲突**（settings 不被改写）；浅色下生效、
`body[data-ds-dark-theme]` 存在时整块不生效（深色零影响）；布局增强（消息列宽度/紧凑间距/
胶囊）与配色解耦，两种配色下都在；cookie 缺失时按「开」处理，老用户升级无感。

### 启动脚本

- 「后端在不在」改为按 HTTP 状态码判断：能拿到任何 1xx–5xx 状态码即视为在监听
- 拉起后端统一带 `--no-open`
- 抓 token 的时机放在端口就绪之后（token 行与就绪几乎同时出现，留约 5 秒重试窗口；
  超时则降级到自签 cookie 通道，仍然可用）

## 三、验证方法（升级官方后可照跑）

### 协议级：自签 cookie 是否仍被接受

比点界面可靠得多，能直接暴露协议漂移：

```bash
# 1. 起后端
node_modules/.bin/dsh web --no-open --port 3110 &
# 2. 从日志取官方 token 入口
grep -o "http://127\.0\.0\.1:3110/?token=[A-Za-z0-9_-]*" /tmp/dsh-web.log | tail -1
# 3. 照第二节的字段约束用 node 自签一枚 cookie，然后：
curl -s -o /dev/null -w '%{http_code}\n' -H "Cookie: $COOKIE" http://127.0.0.1:3110/   # 期望 200
curl -s -o /dev/null -w '%{http_code}\n' -H "Cookie: ${COOKIE%?}X" http://127.0.0.1:3110/  # 期望 401（签名被拒）
```

判读要点：

- **200** = 载荷、authority、签名算法、时间窗全部对齐
- **401** = 协议变了，逐项核对 `browser-auth.js` 的 `encodeCookie` / `isAuthenticated`
- 无 cookie 探测拿到 401/404 都正常（导航与非导航请求路由不同），**不要**据此判断认证是否可用

### 壳级：两条通道各自的端到端

```bash
# 通道一（冷启动）：应打印「已取得本次进程的认证入口」+「走官方 token 入口」
DSH_PORT=3098 DSH_SNAPSHOT=/tmp/cold.png "./desktop/启动 DSH.command"

# 通道二（复用）：先手动起后端，再单独跑壳（不带 DSH_AUTH_URL），应打印「已用本机凭证补浏览器会话 cookie」
DSH_URL=http://127.0.0.1:3099 DSH_SNAPSHOT=/tmp/reuse.png ./desktop/node_modules/.bin/electron desktop/main.js
```

两张截图应渲染出同一页面。若出现认证提示页，说明自签通道失效（先看 `.credentials.yaml` 是否还有该记录）。

### 主题级：token 计算值 + 冷色泄漏扫描

- 读计算值：`getComputedStyle(document.body).getPropertyValue('--dsw-alias-bg-layer-1')` 等应命中 Solarized 色阶
- 冷色扫描：遍历元素，凡「不透明背景且蓝通道显著高于红通道（`b > r + 6`）」且面积较大的即为漏网白框
  （Solarized 暖色系恒有 `r >= b`，这条判据很干净；品牌蓝与官方徽章属已知白名单）

### 功能级：折叠与胶囊

打开一个含工具调用的历史会话，检查：

- `[data-chat-flow] > [data-chat-flow-kind="tool-call"]` 全部 `display: none`（折叠生效）
- `.dsh-tool-strip` / `.dsh-tool-line` / `.dsh-tool-chip` 存在（胶囊生成）
- `.dsh-balance-cell` 显示余额（凭证可用时）

依赖的 DOM 契约（官方 0.1.5 实测仍在，升级后首先核对这几个）：
`data-chat-flow`、`data-chat-flow-kind`（取值 `assistant-step` / `tool-call` / `context` / `user` / `turn-process` / `turn-tail`）、
`data-variant="think"`、`data-tool`、`data-sample="bash"`、
`data-slot="conversation.composer.dock"`、`data-slot="conversation.input.dock"`。

## 四、官方升级自查清单

1. **比对版本**：`npm view @deepseek-ai/dsh dist-tags`，确认 `latest` 与 `desktop/package.json` 锁定值
2. **跑协议级验证**（第三节第 1 条）：自签 cookie 仍返回 200
3. **跑两条通道的端到端**：冷启动与复用各出一张正常页面截图
4. **跑冷色扫描**：无新增泄漏（新增 token 通常伴随新 UI 组件出现）
5. **跑功能级检查**：折叠/胶囊/余额三者俱全，特别是 DOM 契约属性是否被改名
6. **核对主题开关**：`html` 上的 `data-dsh-ux-theme` 是否由首帧脚本写好；
   若再次出现「浅色变纯白」，先查这块闸门是否还在（改造前是 `ctx.get("theme")` 时序问题，
   现在则是 cookie 与注入脚本）
7. **壳控件与官方右上角按钮的遮挡**：新增按钮后确认悬浮控件（`top: 8px; right: 8px`）未压住它们

## 五、已知限制

- 自签 cookie 依赖 `.credentials.yaml` 的 YAML 直排格式（`client-connection/browser-session` 后 400 字符内出现 `secret:`）。
  若官方改变凭证序列化方式，需同步更新 `desktop/main.js` 的读取逻辑
- token 抓取有约 5 秒重试窗口；超时降级到自签通道（功能不受影响，但冷启动会多依赖一次凭证文件）
- 升级脚本清理后端用 `pkill -f "… --port $PORT"` 做子串匹配，理论上 `3080` 会命中 `30801`；
  实际端口取值为固定三位数，风险可忽略，但改造端口策略时需留意
